# Keyfleet authorized security red-team pass — 2026-10-17

Base commit `8edec518` (v82). Authorized by the Keyfleet owner as a defensive
review of a **local/staging checkout only**, with throwaway personas and seeded
data — never the live site, never the shared production database.

This document is the proof table and runbook. The machine-readable catalog is
[`priv/security/redteam_checks.yml`](../../priv/security/redteam_checks.yml);
render and validate it with `mix run scripts/security_proof_table.exs`.

## Method

Code-level attack-surface analysis across three categories (access control &
tenancy, limit & flow bypass, external injection), each check assigned a
verdict with an enforcing `file:line`, then a regression probe that performs the
attack and asserts the safe outcome. Every probe names the local toggle that
disables its control, so the control can be shown to matter: flip it off → the
attack succeeds (probe fails); on → refused (probe passes). Probes that need
real timing, the chain, or a dependency are tagged `:dynamic` and listed for the
Mac's non-sandboxed / fork run.

The suite is additive — it extends the existing security coverage
(`signed_agent_contract_test.exs`, `accounts_policy_test.exs`,
`session_authority_test.exs`, `content_security_policy_test.exs`,
`room_page_test.exs`) rather than duplicating it.

## Headline result

**No exploitable in-repo vulnerability was found.** The codebase is
defense-in-depth: the signed-agent plug derives the actor from the verified
signature (never from the path or body), every money/state action re-derives
"who you may act as" from live chain-projected ownership and gates on an Ash
policy, public reads scope to `open_fleet_ids()`, both Markdown sinks are
sanitized with tight allow-lists, the CSP is `script-src 'self'` with no
`unsafe-inline`/`unsafe-eval`, and the closed-site and coming-soon gates run in
the endpoint before anything is served.

The residual risk is concentrated **outside this repository** and is handed to
the live run:

- **SIWA covered-components / audience / replay** enforcement lives in
  `elixir-utils/siwa` (`Siwa.AgentAuthPlug`). If it is weak, the attacker-chosen
  path `token_id` could ride another agent's signed request. The whole IDOR
  conclusion rests on this binding holding.
- **Privy token verification** (audience/expiry/issuer) lives in `RegentPrivy`.
- **Credit/point debit atomicity** and double-spend live in `RegentCredits` /
  `RegentPoints`. The in-repo agent API only reads balances and builds unsigned
  transactions; it moves no money.
- **On-chain `msg.sender` enforcement** for claim/split/send_share/convert/
  propose/vote decides the real money authority; prove it on an anvil/fork.
- **Notebook-host origin isolation** is a deployment-config invariant (notebook
  host must be a different registrable origin than the app host).

## Shipped vs held

- **No code fix shipped or needed** — nothing was found broken, so there is
  nothing to ship under standing permission and nothing that touches an auth
  boundary to hold. The one genuine, low-severity item is a *regression-coverage
  gap* (the coming-soon gate and the XSS sanitizer were not exercised for the
  money endpoints / non-`<script>` payloads); the new probes close it.
- **Held for the owner's typed go:** nothing here crosses an auth boundary, so
  no hold is required of this pass. The signed-in Git flow, sign-in, secrets,
  production data, wallets, staking, claims and money movement were reviewed but
  **not modified**; any fix they ever need still stops for the owner's go.
- **Staged, not landed:** the suite is on branch
  `claude/security-redteam-1017` (cloud cannot compile, reach the chain, or run
  the live toggles). The Mac compiles it, runs it, gets a Sentinel read, and
  runs the `:dynamic` probes before it lands.

the live/fork run must; **N/A** = pattern absent here.

## Runbook for the live / Mac run

1. **Compile and run the static suite** on the local/staging checkout:
   `mix test test/keyfleet_web/security` — every non-`:dynamic` probe should
   pass (the control is on). Then `mix run scripts/security_proof_table.exs` to
   confirm the catalog and the suite agree.
2. **Prove each control matters** (the off/on proof): for a check, apply its
   `disable_toggle` from the catalog, re-run its probe (it should now fail — the
   attack succeeds), then revert and confirm it passes (refused). Do this on the
   local checkout only; never ship a toggle change.
3. **Run the `:dynamic` probes**: `mix test test/keyfleet_web/security --include dynamic`,
   on a **non-sandboxed** DB for the concurrency/idempotency timing.
4. **Close the out-of-repo items** against the dependencies and chain:
   RT-CREDIT-SPEND (race the `RegentCredits` spend on a 1-credit balance),
   RT-SESSION (Privy token audience/expiry), RT-SSRF (notebook-hub host can't
   reach internal), on-chain `msg.sender` for the money actions on an anvil/fork
   (`make check-audit-fork`), and RT-NOTEBOOK-ORIGIN (assert the notebook host is
   a different origin than the app and no app cookie is returned on it).
5. **Record each dynamic result** back into the catalog's `dynamic_note` and
   re-render this table.
